# Added Staging Branch to Nixpkgs PR Branch Tracker

Date: 2026-02-07T19:33:47Z

## Context

While investigating why [NixOS/nixpkgs PR #480465][pr-480465] ("go_1_25:
1.25.5 -> 1.25.6") appeared as not available in any tracked branch, the root
cause was identified: the PR was merged into the `staging` branch, which was
not included in the script's tracked branch list.

The script only tracked `master`, `staging-next`, `nixos-unstable`,
`nixpkgs-unstable`, and `nixos-unstable-small` — it did not track `staging`.
The commit was sitting in `staging` waiting to be merged into `staging-next`,
which then flows into `master`, and eventually into the channel branches. This
is expected behavior for the nixpkgs branching model — PRs with large rebuilds
(like Go compiler updates) go through `staging` → `staging-next` → `master` →
channels. PR #480465 was merged on 2026-01-16T07:22:36Z and had simply not
propagated yet.

## How to Determine Whether a PR Targets Staging or Master

The target branch is visible in the `base.ref` field of the [GitHub PR API
response][github-pr-api]. When a contributor creates a PR against nixpkgs, they
choose the base branch according to the [nixpkgs contribution
guidelines][nixpkgs-contributing]:

- **`master`** — PRs that cause zero or few rebuilds (small package updates,
  documentation changes, new packages).
- **`staging`** — PRs that cause a large number of rebuilds (compiler updates,
  core library changes, toolchain bumps). These are batched and merged together
  into `staging-next` periodically to avoid overwhelming the build
  infrastructure.
- **`staging-next`** — Rarely targeted directly; usually receives merges from
  `staging`.

For example, the GitHub API response for PR #480465 includes:

```console
$ gh pr view 480465 --repo NixOS/nixpkgs --json baseRefName --jq '.baseRefName'
staging
```

This indicates the PR was merged into `staging`, not `master`. The full
propagation path for such PRs is:

```text
staging → staging-next → master → channel branches
```

The channel branches (`nixos-unstable`, `nixpkgs-unstable`,
`nixos-unstable-small`) are automatically advanced by Hydra (the NixOS CI
system) once all required builds and tests pass.

## Smart Branch Filtering by Base Branch

### Problem

After adding `staging` to the tracked branches, the script always displayed all
six branches for every PR — even when some branches were irrelevant. For
example, a PR targeting `master` would show `staging` and `staging-next` with
⚠️ warning indicators, which is misleading because master-targeted PRs never
flow through the staging pipeline.

### Solution

Implemented smart branch filtering based on `json.base.ref` (the PR's target
branch). The script now reads the PR's base branch from the API response and
only shows branches relevant to the commit's propagation path:

| PR Base Branch | Branches Shown | Branches Hidden           | Rationale                                                 |
| -------------- | -------------- | ------------------------- | --------------------------------------------------------- |
| `master`       | 4              | `staging`, `staging-next` | Master PRs don't flow through staging pipeline            |
| `staging`      | 6 (all)        | (none)                    | Full pipeline: staging → staging-next → master → channels |
| `staging-next` | 5              | `staging`                 | Enters at staging-next, skips staging                     |
| Other/unknown  | 6 (all)        | (none)                    | Safe default                                              |

### Files Changed

- `nixpkgs/nixpkgs.js` — Updated `processResponse()` to filter
  `subscribedBranches` based on `json.base.ref` before creating branch
  metadata and fetching status.
- `nixpkgs/nixpkgs.utils.js` — Added `getRelevantBranches(baseBranch,
allBranches)` utility function with full JSDoc documentation.
- `nixpkgs/nixpkgs.mocks.js` — Added `mockStagingPR` (staging-targeted) and
  `mockStagingNextPR` (staging-next-targeted) mock fixtures.
- `nixpkgs/nixpkgs.utils.test.js` — Added 29 new tests covering:
    - `getRelevantBranches` unit tests (master, staging, staging-next, unknown,
      edge cases)
    - Integration tests with all mock PRs verifying correct filtering
    - `createBranchMetadata` with filtered branch lists
